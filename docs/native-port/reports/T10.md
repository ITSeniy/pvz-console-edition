# T10 — общий механизм нативных замен

## 1. Итог

Реализованы общий механизм, оба пилота, CTest, proof runner и шаблон следующих
замен; replay_end, первые 16 входных LR и принятые CSV/JSON в git подключены
по решению «Приёмка». Два полных запуска без параметров на одном EXE дали
**0 / 0**, каждый — **57/57 критериев**, **120 000 кадров**, **20/20 равных пар**
и 0 ошибок сравнений; полный внешний `-InjectError` дал **1** исключительно
из-за обнаруженных инъекций, при тех же 120 000 кадрах и 20/20 равных пар.
Изменения перенесены в основную папку, там сборка и CTest **16/16** прошли;
предыдущая полная серия штатных регрессий — 274/276 с двумя vases_pc-отказами,
ожидания и пороги сохранены.

## 4. Результаты

### 4.1. Контракт и имена — проверено по Xbox

Второй пилот: полное листовое тело 82130E50..82130F4C,
generated/default/pvz_recomp.24.cpp. ABI: r3=Rect* (sret), r4=Board*;
r3 сохраняется, результат — четыре big-endian u32 по +0/+4/+8/+12.
Единственные stores — эти 16 байт. Вызовов, stack stores, RNG, времени,
IO и аллокаций в теле нет; изменения scratch-регистров не являются выходами.

| Xbox | Проверенное действие |
|---|---|
| 82130E50..E94 | Board+1A4 → SeedBank+40; count≤6:0, 7:60, 8:76, 9:112, иначе153 |
| 82130E98..EC4 | Board+F4 → LawnApp; x=456+extra, width=70, height=72, y=0 |
| 82130EC8..F18 | app.board(+900) и mode(+9CC)=19 либо50 → x=600 |
| 82130F1C..F4C | mode в [77,89] → x=330 |

Имя подтверждено полным алгоритмом и потребителями, а не одним литералом:
именованный Android Board::GetShovelButtonRect по 0015463C (80 байт) и
GetSeedBankExtraWidth по 00154614 (40 байт) дают тот же набор extra, размеры
70×72 и ветви 600/330. PC Board.cpp:1307 — дополнительный ориентир имени.
Android-смещения +20C/+34 не перенесены: используются проверенные Xbox
+1A4/+40. Реализация написана по Xbox; GPL/LGPL-код не копировался.

**Проверено изолированно:** actual-source harness сравнил новое тело с полной
неизменённой generated-функцией на **31 104** случаях:
16 значений count (включая INT_MIN/MAX) × 162 mode (-1..160) × 2 app.board ×
6 выходных указателей, включая aliasing с полями входа. Совпали все байты
буфера и r3.u64. Сохранён порядок stores/повторного чтения app.board.
Эти случаи не включены в живой охват.

PixelToGridX: алгоритм T06 сохранён, результат r3 сравнивается полностью,
Signed/64. Дополнительно объявлены entry.r1-32..entry.r1-1: сохранённый
Zen-helper 82291A00..82291B88 пишет четыре 8-байтовых conversion slots.
Его полное тело прочитано по образу: других stores и дочерних вызовов нет.
В обычной координатной ветви этот диапазон не меняется.

Для обоих пилотов объявление покрывает все guest writes native/оригинала;
выходные буферы обычных вызовов — стек вызывающего. Будущие функции с эффектами
вне объявленных выходов должны использовать Safety::SnapshotsOnly, сравнение
которого отвергается до исполнения native.

### 4.2. Механизм и CTest — проверено кодом и запуском

Одно объявление создаёт три прежних по смыслу флага; compare_all включает
сравнение всех зарегистрированных замен. Флаги init-only, как фактически
кэшировавшиеся значения T06. Без активных флагов — один статический bool,
__imp__ и возврат; диапазоны/контекст/guest-память не читаются механизмом.

При compare: входные байты → native на копии контекста → сохранение результата →
восстановление входных байтов → original → точное сравнение → выбор объявленных
выходов. Остальной контекст сохраняется от original. Без compare исполняется
только выбранная версия; inject_error не действует.

Различия всегда логируются с GPR/FPR аргументами, r1 и адресами/значениями
отличающихся байтов. Период — 1000 сравнений. Replay_end содержит первые 16
различных входных ctx.lr с числом сравнений/ошибок и остаток other; сумма
проверяется parser. Учёт LR идёт под тем же mutex, значение берётся до native.
Отображённый файл
<log>.<name>.native-counts.bin хранит два атомарно публикуемых слота с точными
завершёнными сравнениями/ошибками; последний оборванный publish оставляет
предыдущий слот. Валиден и начальный 0/0/0; нулевой общий охват всё равно отвергается.

На раннем этапе native_replacement_test отдельно пересобран и прошёл, EXE игры
оставался f34f986b… . Добавлен mismatch в последнем байте второго диапазона:
проверяются все байты и восстановление конца диапазона.
Parser self-test после доработки: **18 проверок** (включая обрыв checkpoint до первого вызова,
ротированные журналы, испорченную/отсутствующую сводку, zero coverage и
удаление повторённых CLI-флагов, корректный нулевой LR-список, отсутствие
разбивки, неверную сумму/повтор LR и некорректный overflow).
После доработки `.\build.bat test`: **16/16**, код 0;
вывод — runtime-data/t10-revision-ctest.log; после согласованного UI-фикса
также **16/16**, t10-ui-sync-ctest.log. C++-тест проверяет сохранение
первых 16 разных входных LR, два последующих адреса в other и ошибки обеих групп.
Actual-source harness после доработки также прошёл 31 104 случая;
runtime-data/t10-revision-actual-check.log.

Решения:
1. **`src/input_replay.cpp`: разрешено.** Добавить include и вызов
   `pvz::native::ReplayCompleted()` после обоих сообщений «replay completed». Больше в

2. **Нормативная метрика повторяемости.** Критерии «счётчики равны T06» и «повтор даёт те
   же счётчики» снимаются. Это ошибка карточки: функции вызываются и из отрисовки, а число
   кадров отрисовки на логический шаг зависит от реального времени. Норма теперь такая:
   - 0 ошибок;
   - не меньше 10 000 реальных сравнений на замену по всем сценариям; нулевой охват
     сценария указывается явно;
   - снимки равны;
   - отрицательный контроль пойман;
   - повторный прогон даёт тот же итог.

   Счётчики — справочные. Сводку на `replay_end` дополнить разбивкой по вызывающему
   (`ctx.lr`, первые 16 адресов). В отчёте показать, у каких вызывающих A/B расходятся, и
   по T11 указать, относятся ли они к отрисовке. Порогом это не делать.

   Zen (4916/5000) остаётся открытым вопросом пути записи и приёмку не блокирует.
4. **Регрессии.** `vases_pc_*` — известная нестабильность раскладки ваз, решение отдельное.
   Ожидания не трогать.
