# Приёмка результатов

Порядок проверки работы агента. Цель — убедиться, что результат вменяемый, воспроизводимый
и не выходит за рамки задачи. Мерило не «агент сказал, что готово», а собственная проверка.

## 1. Быстрый отсев (5 минут)

- [ ] Есть отчёт `reports/Txx.md` со всеми семью разделами из [agent-guide.md](agent-guide.md#7-отчёт).
- [ ] `git status` и `git diff --stat`: изменены только файлы из раздела «Результат» карточки.
      Нет правок в `generated/`, `assets/`, образах, `research/pvz-pc/`.
- [ ] Нет коммитов и смены ветки, если карточка их не требовала (`git log -3`, `git branch --show-current`).
- [ ] Каждый пункт критериев приёмки отмечен с доказательством, а не словом «выполнено».

Если что-то не так, вернуть задачу без дальнейшей проверки.

## 2. Воспроизведение

- [ ] Выполнить команды из раздела «Как воспроизвести» с нуля. Удалить прежний вывод
      скрипта, если он есть.
- [ ] Числа в отчёте совпадают с полученными.
- [ ] Для кода: `.\build.bat test` проходит; затронутые регрессии из `scripts/run_*_regression.ps1` проходят.
- [ ] SHA-256 входов в выводе совпадает с нашими файлами.

## 3. Выборочная проверка по существу

Проверять выборку, а не верить сводке. Выбор — случайный (`random.sample` с записанным seed),
а не первые строки таблицы.

| Тип результата | Что проверить |
|---|---|
| Имена функций (T01, T02) | 20 случайных имён на уровень уверенности. Для каждого сравнить Xbox-функцию (Ghidra/Capstone) с Android-функцией: число и порядок вызовов, строки, константы, размер. Отдельно — 5 известных якорей из `src/` |
| Смещения полей (T04) | 10 случайных полей: найти в Xbox-коде инструкцию, которая читает/пишет поле в функции с известным именем, и сверить смысл с PC/Android |
| Опись (T03, T09) | 10 случайных строк описи сверить с исходным файлом или данными |
| Нативная замена (T06) | Сравнение реплеев с заменой и без: одинаковые снимки. Затем вручную испортить замену (например, +1 к результату) и убедиться, что сравнение это ловит |
| Расследование (T07, T08) | Каждое утверждение о причине подкреплено адресом и наблюдением в журнале или отладчике; предложенный фикс опирается на причину, а не на симптом |

Записать в отчёт проверки (раздел «Приёмка» в конце `reports/Txx.md`): seed, число
проверенных, число ошибок, вывод.

**Порог для имён:** в выборке уровня high нет ни одной ошибки; в medium — не больше 2 из 20.
Иначе уровень понижается или задача возвращается.

## 4. Признаки халтуры

- Метрика подогнана: пороги изменены после первого прогона, «неудобные» случаи исключены без объяснения.
- Проверка проверяет сама себя: например, имена сверяются с тем же источником, из которого получены.
- Уверенность без признаков: high выставлено по одному слабому признаку (только размер функции).
- «Проверено» без команды или адреса.
- Скопирован код из GPL/LGPL-проектов (искать характерные имена `old_*`, `homura::`, комментарии на китайском).
- Отключённые или удалённые тесты, `#if 0`, увеличенные таймауты.
- Отчёт длиннее и увереннее, чем позволяют данные.

## 5. Решение

| Итог | Действие |
|---|---|
| Принято | Обновить статус в `README.md`; при необходимости перенести таблицу в `data/`; предложить владельцу коммит |
| Принято с замечаниями | Записать замечания в отчёт; вынести недоделанное в новую карточку |
| Возвращено | Ответить агенту (или в новой сессии) конкретным списком: что не так и как проверить исправление |
