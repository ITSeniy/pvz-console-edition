## 3. Как воспроизвести

Команды из корня worktree. Нужны полный runtime-комплект сборки (в том числе
`build/mouse/*.ptx`), данные `assets` и исходный профиль
`runtime-data/zen-shop-probe-user`. В этой проверке использован один готовый
EXE master; изменения скриптов пересборки игры не требуют.

```powershell
./build.bat test
./scripts/run_feedback_regression.ps1
python scripts/check_feedback_regression.py
./scripts/run_multiplayer_regression.ps1
python scripts/check_multiplayer_regression.py
./scripts/run_services_regression.ps1
python scripts/check_services_regression.py
./scripts/run_shop_regression.ps1
python scripts/check_shop_regression.py
```

Повторить всю последовательность три раза, сохраняя после каждого набора
`runtime-data/*-regression-runs.json` и `*-regression-validation.json`;
у Services checker использует `services-feedback-validation.json`.
Ненулевой код Feedback/Services ожидаем при двух известных отказах и не должен
мешать запуску остальных наборов. Явный `-Deterministic` равнозначен запуску
без ключа. Для прежнего режима добавить `-WallClock` к каждому runner.

Шаговые CSV уже сохранены, перезаписывать их для обычного прогона не нужно.
Воспроизведение преобразования отдельной записи:

```powershell
# Сначала записать исходный секундный CSV с теми же игровыми аргументами:
# ... --pvz_deterministic_seed=42 --pvz_deterministic_clock=1792195200
#     --pvz_replay_record_steps=true (без frame_locked).
python -I scripts/replay_seconds_to_steps.py <исходный.csv> <оригинальный.log> --output <новый.steps.csv>
```

Использован существующий путь T05b/T10, без интерполяции FPS и ручного изменения
номеров шагов. Конкретные исходники/журналы/хеши находятся в каждом `.csv.json`.

Измерительные помощники и крупные доказательства остаются в игнорируемом
`runtime-data/t12/`. Три серии запускались одновременно в изолированных
`worker-1..3`; внутри каждой все 44 процесса последовательны. EXE, DLL,
ресурсы курсоров и исходные профили одинаковы, логи, cache и рабочие копии
профилей раздельны. База запускалась сохранёнными runner master и smoke master,
с заменой только пути рабочего каталога измерительного помощника.
Для повторения именно этой локальной схемы (после завершения текущих запусков):

```powershell

$N=1
```

### Причина нестабильных кадров

Проверено по журналам и чтением `src/frame_capture.cpp`: штатный capture
начинает отсчёт после OnPostLaunchModule и назначает следующий кадр после
завершения предыдущего CaptureGuestOutput/сохранения. Прежний smoke отсчитывал
Seconds от Start-Process. Для VS (80s, delay 30s, interval 5s) десятый кадр
приходится на 75s **после запуска capture**, и задержка старта оставляла
8–9 кадров вместо нужных десяти. Даже окно после title не исключает задержки
хоста: в Garden зафиксирован разрыв между кадрами 11/12 в 20 секунд,
из-за чего серия заканчивалась с 14 вместо 16. Точные разрывы серий 1/3:
19.968s и 20.518s между кадрами 11/12 (`capture-gaps.json`, строки журналов
319→367 и 319→366); число «20» здесь округлено.

Default теперь ждёт готовности (`wait_title ready` либо delivery row 0),
выдерживает прежнее минимальное Seconds, затем при необходимости ждёт все
запрошенные штатные кадры и реальное завершение реплея. Предел старта 120s,
дополнительного ожидания 120s; при превышении runner прекращается с ошибкой.
`finally` освобождает процесс и при ошибке чтения журнала.
Снимки остаются на исходном настенном расписании: delay, interval, count,
размер и пороги checker не изменены; переноса снимков на шаги нет.
Максимальное фактическое дополнительное ожидание финальных запусков —
**55.529s**. Их окна и результаты сохранены в `execution.smoke_window`
и `execution.capture_window`, полные аргументы — в `execution.game_arguments`.

В `locked-v3` первоначальный вызов Shop checker с `python -I` не нашёл его
локальный импорт `input_audit_manifest`, а помощник скопировал старый validation.
Это ошибка измерительного помощника агента, не повторный отказ игры.
Недействительные файлы сохранены как `STALE-validation.json` и
`invalid-isolated-python-check.log`; они исключены из всех таблиц.
Неизменённый checker повторно выполнен обычным Python по тем же свежим
12 игровым процессам и дал 70/70 × 3. Остальные наборы этой серии продолжены
с сохранением её Shop; игровые runner/smoke/реплеи в течение серии не менялись.
Помощник теперь требует свежий validation, предварительно убирая старый;
подробности — `locked-v3-checker-recovery.txt` и progress.jsonl.
Позднее эта попытка остановлена из-за настоящего timeout Last Stand,
описанного выше; `locked-v3-attempt-note.txt`. Она частичная и не входит
в три полные итоговые серии.

### Полная таблица исходов

этапа. Это все 276 проверок, включая неизменившиеся.

## 6. Не проверено и риски

- Проверена воспроизводимость набора checker-исходов на данном EXE и хосте,
  а не тождество RAM/пикселей, произвольные нагрузки или другой GPU/EXE.
- Во многих сценариях остаётся секундная доставка; новые условия могут
  обнаружить дополнительный короткий импульс. Лимит ожидания сообщает отказ,
  а не гарантирует завершение при неограниченной задержке хоста.
- Крупные журналы/кадры и измерительные помощники локальны и игнорируются git.
  Для переноса доказательств нужен весь runtime-data/t12 и исходные logs;
  JSON конвертации сохраняет абсолютные пути этой машины.
- Совместимый журнал меняет только написание completion. При независимой
  проверке следует читать также raw_logs, их хеши и delivery rows.
- T07b и исходный vases-сценарий остаются известными отказами.
