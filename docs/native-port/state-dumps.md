# Снимки состояния и сравнение реплеев (T05)

## Диагностический режим T05b

Новые параметры отключены по умолчанию. `--pvz_deterministic_seed=42`
передаёт десятичный u32 в локальный seed wrapper `824943A0`; пустое значение
сохраняет оригинальный seed, `0` является допустимым seed. Импорт
`KeTimeStampBundle`, uptime и часы других подсистем не подменяются.

`--pvz_replay_frame_locked=true` читает CSV с обязательной первой строкой
`# pvz-frame-locked-v1`. Первая колонка — целый номер **входящего логического
обновления приложения**, начиная с 0, остальные три колонки сохраняют прежний
формат. Это отдельная шкала от `frame` в JSONL: дамп начинает запись позднее,
после собственного условия готовности сцены. События одного шага публикуются
синхронно в порядке строк перед оригинальным `8247FFC0`; отдельный replay thread
в этом режиме не создаётся. Проверка `wait_*` становится утверждением о готовности
на заданном шаге: ошибка явно записывается в журнал, последующие события не
публикуются. Скрытого переноса события на другой шаг нет.

Шкала секунд не пересчитывается предположением о частоте кадров. Для получения
CSV сначала записывают существующий секундный реплей с
`--pvz_replay_record_steps=true` и тем же seed/профилем, затем выполняют:

```powershell
python -I scripts/replay_seconds_to_steps.py tests/replays/feedback_heavy_console.csv logs/RECORDED-RUN.log --output runtime-data/heavy-steps.csv
```

Конвертер требует все строки ровно один раз, отвергает повторные, пропущенные и
убывающие шаги; создаёт новый CSV и `.csv.json` с SHA-256 исходного CSV, журналов,
конвертера и результата. Существующие доказательства не перезаписываются.
Запись секундного режима — наблюдаемая доставка со старым опросом 25 мс;
переведённая последовательность задаёт фиксированное расписание нового режима,
а не обещает повторить исходный процесс побайтно.

Например, для каждой рабочей копии профиля отдельно:

```powershell
.\smoke.ps1 -Seconds 52 -UserDataRoot runtime-data/MY-RUN/user --pvz_test_unlock=true --pvz_mouse_cursor=true --pvz_replay_controller=true --pvz_cursor_mode=console --pvz_vsync=false --pvz_pause_on_focus_loss=false --pvz_deterministic_seed=42 --pvz_replay_frame_locked=true --pvz_input_replay=runtime-data/heavy-steps.csv --pvz_state_dump=runtime-data/MY-RUN/state.jsonl --pvz_state_frames=3000
```

**Xbox-доказательство точки:** `8247FFE8..8248000C` проверяет app+`5A7`, вызывает
`824A6140` с manager из app+`36C`; `824A617C` вызывает виртуальный логический
update. Существующий хук `824A6140` сначала вызывает `DispatchWidgets`, поэтому
события публикуются до его обработки и обновления Board. Хук T05 `82492618`
не изменён. `821A5E9C..821A5EC0` увеличивает app+`A0C` на единицу и вызывает
`824DEB00` → `8247FFC0`; дробный путь `824752F0` → `824A6198` отдельный.
Корневой логический update не принимает переменный `dt` параметром. Таймеры и
дробные обновления дополнительно оцениваются по фактическим парам в отчёте T05b;
одного этого статического факта недостаточно для утверждения о детерминизме.

Без новых флагов wrapper и app update вызывают оригиналы; секундный replay,
его поток, ожидания и существующие CSV сохраняются. Результаты запусков,
неустранённые расхождения и ограничения перечислены в `reports/T05b.md`.

`--pvz_state_dump=<file.jsonl>` записывает состояние после каждого **логического**
обновления корневого WidgetManager. Вложенные виджеты, включая Board, уже обновлены.
Дробное обновление анимаций и GPU Present не считаются отдельными шагами симуляции.
Снимки покрывают меню, создание/удаление Board, Adventure, Versus и прочие режимы.

Существующие CSV-реплеи **не детерминированы**: штатный RNG получает seed из
платформенного времени, а события публикуются отдельным потоком по настенным часам.
Инструмент обнаруживает расхождения; он не объявляет разные состояния эквивалентными.
Перед доказательством большой нативной замены потребуется диагностический режим
с управлением RNG и доставкой событий по шагам игры. Это не исправление обычного режима.

## Запуск

```powershell
.\build.bat
.\build.bat test

# Пять существующих реплеев, каждый дважды, отдельные копии профилей:
.\scripts\run_determinism_check.ps1

# Один сценарий, две копии одного начального профиля:
.\scripts\run_determinism_check.ps1 -Cases minigame -OutputRoot runtime-data/state-dumps/my-minigame

# Проверка чувствительности на фактической guest-памяти:
.\scripts\run_determinism_check.ps1 -Cases minigame -Repeats 1 -Sensitivity -OutputRoot runtime-data/state-dumps/my-sensitivity

# Тот же реплей с измерением логического обновления, без записи снимков:
.\scripts\run_determinism_check.ps1 -Cases minigame -Repeats 1 -ProfileOnly -OutputRoot runtime-data/state-dumps/my-profile

python -I scripts/compare_state_dumps.py path/to/a.jsonl path/to/b.jsonl --output runtime-data/state-comparison.json
```

`OutputRoot` должен быть новым каталогом. Результаты не перезаписываются. По умолчанию
используется `runtime-data/state-dumps/<timestamp>`; исходный пользовательский профиль
не запускается и не редактируется. Рабочие копии создаются отдельно для каждого процесса.
Adventure начинается с нового профиля; остальные сценарии — с копии
`runtime-data/zen-shop-probe-user` (меняется параметром `-Baseline`).

При самостоятельном запуске:

```powershell
.\smoke.ps1 -Seconds 70 --pvz_mouse_cursor=true --pvz_test_unlock=true --pvz_vsync=false --pvz_input_replay=F:/src/PVZXboxRecomp/tests/replays/adventure_mouse.csv --pvz_state_dump=F:/src/PVZXboxRecomp/runtime-data/state-dumps/adventure.jsonl --pvz_state_frames=5000
```

Флаги диагностики задаются **при запуске процесса**:

| Флаг | По умолчанию | Значение |
|---|---|---|
| `pvz_state_dump` | пусто | Путь к JSONL; пустой путь отключает запись и чтение состояния |
| `pvz_state_frames` | 0 | Максимальное число записанных шагов; 0 — до завершения процесса |
| `pvz_state_profile` | false | Измерять стоимость root update и записи; можно использовать без dump |
| `pvz_state_inputs_sha256` | пусто | SHA-256 внешнего манифеста входов, который создаёт runner |
| `pvz_state_mutate_frame` | 0 | Проверка чувствительности: +1 солнце на указанном кадре; 0 — выключено |

После достижения `pvz_state_frames` игра и реплей продолжают работать. Лимит даёт
сравниваемые захваты одной длины, независимо от миллисекунды завершения `smoke.ps1`.
Первый записанный шаг имеет `frame=0`. Запись начинается, когда появляется главный
экран (scene 1, корень MainMenu) либо Board; загрузочные update до этой точки пропускаются.
Меню может содержать демонстрационную Board режима 73 — это штатное наблюдаемое
состояние, а не доказательство прохождения Adventure. Runner отдельно требует
`scene=3` и целевой игровой mode в покрытии каждого игрового сценария.

Без dump/profile новый хук сразу передаёт управление оригиналу. Он не читает
guest-поля, не открывает файл, не берёт время и не меняет RNG. Сам переход через
функцию-хук и проверка двух сохранённых bool остаются.

## Схема JSONL

Первая строка — metadata: schema 1, фаза `after-root-update`, название хеша,
формат RNG, закреплённый SHA-256 XEX и SHA-256 манифеста runner. Снимки начинаются
со следующей строки. В каждом снимке:

- `frame`: последовательный номер логического шага захвата.
- `mode`, `scene`: значения LawnApp; `root_vtable`: постоянный адрес таблицы
  корневого сфокусированного виджета (0 при отсутствии фокуса).
- `board`, `paused`, `sun`, `sun_p2`: наличие проверенной Board, пауза, солнце обоих игроков.
- `rng_index`, `rng_hash`: индекс и хеш всех 624 слов глобального RNG вместе с индексом.
- `plants`, `zombies`, `projectiles`, `coins`: `null` без Board, иначе описание массива.

Для каждого массива сохраняются:

| Поле | Что проверяет |
|---|---|
| `valid` | Корректность диапазона, счётчиков и числа выделенных ID |
| `count` | Число выделенных объектов с mDead=false |
| `allocated`, `used`, `next_key` | Счётчики и последовательность ID в DataArray |
| `ids`, `type`, `x`, `y`, `health`, `state` | Отдельные хеши соответствующих полей по порядку слотов |
| `hash` | Совокупный хеш ID, типа, XY, здоровья, состояния |

У монет/снарядов нет здоровья: соответствующее значение в хешировании равно нулю.
Здоровье зомби — здоровье тела; шлем/щит в эту версию схемы не входят.
Позиции растений — целочисленные поля; зомби/снаряды/монеты — исходные биты float.
Нет округления и epsilon; различается даже изменение одного бита float.

Хеш — FNV-1a 64-bit над четырьмя big-endian байтами каждого выбранного u32.
В хеш не попадают адрес выделенного блока, указатели объектов, padding, свободные
слоты или графические ресурсы. Порядок слотов и ID учитывается. `valid=false` означает
негодный захват: сравнение завершится ошибкой, а не успешным совпадением двух ошибок.

## Сравнение

```powershell
python -I scripts/compare_state_dumps.py a.jsonl b.jsonl
```

Коды завершения: **0** — полное совпадение; **1** — различие; **2** — ошибка чтения,
схемы, несовместимые metadata или неполный захват. Вывод и `--output` содержат
SHA-256 обоих входов, первое поле/кадр и значения с обеих сторон, число отличающихся
кадров, частоты отличающихся полей и покрытие сценария.

Сравниваются все поля state. Сдвиг кадров, пропуск RNG, допуски для float и игнорирование
последнего повреждённого JSON не применяются. Пропуск/дубликат кадра, пустой файл,
metadata без снимков, duplicate JSON key или обрезанная последняя строка — ошибка.
Путь файла и SHA манифеста — provenance, они не являются состоянием игры; phase,
schema, hash, rng и XEX должны быть совместимы. Сборки оригинала/замены могут иметь
разные хеши EXE, поэтому EXE хранится во внешнем манифесте и не участвует в равенстве state.

## Чувствительность

При `pvz_state_mutate_frame=N` рядом создаётся `<dump>.control.jsonl`. На кадре N:

1. Полное состояние до вмешательства пишется в контрольный поток.
2. В **guest-памяти** Board+55F4 увеличивается на единицу.
3. Новое состояние пишется в основной поток.

На остальных кадрах обеим копиям передаётся одинаковый снимок фактической игры.
Поэтому первая разница должна быть ровно `frame=N`, поле `sun`, значение +1.
Это проверка пути «память → снимок → файл → сравнение» внутри одного запуска;
она намеренно изолирована от недетерминизма двух разных процессов. Контрольный поток
после N тоже наблюдает уже изменённую игру; он не является второй симуляцией.
Если на N нет Board, журнал сообщает ошибку, а runner отклоняет проверку чувствительности.

## Измерение стоимости

`pvz_state_profile=true` пишет каждые 500 root updates:

```text
PvZ state timing batch ... update_us_p50 ... update_us_p95 ... dump_us_p50 ... dump_us_p95 ...
```

`update_us` — время оригинального обхода корня с существующими хуками и дочерними
Board updates; `dump_us` — сбор выбранных полей, хеширование, форматирование и
синхронная запись с flush. Это время **шага CPU**, не GPU frame time и не интервал Present.
Runner сохраняет измерения в summary.json для dump и ProfileOnly. Сравнивать нужно
интервалы с активной записью: ранние batch до начала capture и batch после лимита
показывают только стоимость проверки условий.

Источник счётчика проверяется отдельно: `822CA100` читает указатель импорта
`82000850`, затем слово по `+10` (hex). В исходном образе импорт содержит
`000100AD`: ordinal `AD` — `KeTimeStampBundle` (локальный
`research/rexglue-source/src/kernel/xboxkrnl/export_table.inc:187`). В
`xboxkrnl_module.cpp:183..199` это 24-байтная структура; поле +16 (decimal)
получает `QueryGuestUptimeMillis()` и обновляется таймером раз в 1 мс.
Это подтверждает зависимость seed от времени запуска; код SDK здесь прочитан
как доказательство значения платформенного импорта, а не скопирован в порт.

## Границы доказательства

Снимок — выбранная проекция состояния, а не сериализация всей игры: отсутствуют
полные анимации, UI-дерево, все таймеры растений, щиты/шлемы, challenge state,
seed banks, RNG отдельных объектов и состояние host input queue. Совпадение проекции
не доказывает эквивалентность произвольной подсистемы. Перед T06/T07 набор полей нужно
расширить под конкретную заменяемую функцию; несовпадение уже достаточный сигнал ошибки.

Windows-проверка VirtualQuery защищает обход от явно неотображённых диапазонов;
на остальных платформах есть только проверки диапазонов u32/счётчиков. Многопоточные
изменения RNG не замораживаются и не маскируются. FNV-1a — диагностический,
некриптографический хеш с ненулевой вероятностью коллизии.

Обычный реплей оставляет физический ввод и скорость доставки событий в рамках
существующего механизма порта. Для текущих чисел детерминизма и проверки чувствительности
см. [отчёт T05](reports/T05.md); его таблица не заменяет запуск PS3/Android или полный playthrough.

## Детерминированный диагностический режим T05b

Реализация T05b находится в отдельном worktree. Флаги задаются при запуске;
пустой seed и false для обоих replay-флагов сохраняют прежний путь исполнения.
Существующие CSV в секундах не изменены.

| Флаг | По умолчанию | Действие |
|---|---|---|
| `pvz_deterministic_seed` | пустая строка | Десятичный u32, включая 0, вместо аргумента seed wrapper `824943A0` |
| `pvz_replay_record_steps` | false | Обычный seconds replay пишет `PvZ replay recorded row R step S` после доставки каждой строки |
| `pvz_replay_frame_locked` | false | Отключает seconds-thread; доставляет строки нового CSV синхронно перед логическим update |
| `pvz_replay_rng_trace` | пусто | Дополнительная медленная диагностика: JSONL вызовов глобального MT с шагом, host thread и LR |

Seed не подменяет `KeTimeStampBundle` и другие платформенные часы. Неверный
seed пишет ERROR и оставляет исходную инициализацию; такой запуск не является
доказательством детерминизма. Флаг устанавливает seed при каждом обращении к
этому wrapper, а не замораживает результаты генератора или состояние RNG.

Конвертер использует **фактически записанные шаги**, а не умножение секунд на
100. Нумерация строк начинается с 0, без комментариев/пустых строк. Новый CSV
начинается строкой `# pvz-frame-locked-v1`, затем имеет прежние четыре колонки,
но первая — неотрицательный целый логический шаг. Повторная запись поверх
существующего CSV/манифеста запрещена конвертером.

```powershell
# Новая копия одного исходного профиля на КАЖДЫЙ запуск.
New-Item -ItemType Directory runtime-data/t05b-review
Copy-Item runtime-data/zen-shop-probe-user runtime-data/t05b-review/record-user -Recurse
```

### Точки синхронизации и отличие от обычной симуляции

`8247FFC0` проверяет app+5A7 и вызывает корневой WidgetManager через `824A6140`.
T05b перед этим вызовом увеличивает app replay step и публикует события.
Очередь обрабатывают существующие input hooks; обработчики и фикстуры не
переписаны. Доставка всех строк одного шага сохраняет порядок, включая batches.
Wait не ждёт host time: неготовность экрана, пропущенный шаг, неверный header
или CSV фиксируются как ERROR и останавливают дальнейшую доставку. Сам процесс
игры продолжает работать, поэтому выживший smoke **не означает** успешный replay:
нужно проверить отсутствие этих ошибок и строку `PvZ frame replay completed`.

App replay step начинается на загрузке. `state.frame=0` начинается позднее,
когда T05 увидел MainMenu/Board. Это разные начала отсчёта; переносить номер
из одного пространства в другое без записи нельзя. В seconds-record загрузка
и дискретность потока всё ещё влияют на записанные шаги; после конверсии оба
сравниваемых процесса используют один и тот же неизменный steps.csv.

Одних seed и step replay оказалось недостаточно. По Xbox установлены ещё
две зависимости порядка обновлений:

- `824752F0` пересылает переменное fractional f1 в `WidgetManager::UpdateF`
  (`824A6198`), проверяя app+6B4/+5A7. Под frame-locked его штатные вызовы
  подавлены; после каждого app root logic original вызывается ровно один раз
  с f1=1.0 — одна нативная единица дробного шага (логическая сетка 100 Гц).
  Это не требование 100 Present/с и не подмена глобальных часов.
- `CutScene::Update` на `8217C7D8..E0` ждёт Board+560C>0 перед preload и
  `PlaceStreetZombies` (`82179590`). Поле увеличивает настоящий `Board::Draw`
  (`82146A60`, записи `82146B74/94`). В `DoUpdateFrames` (`82478108`) под
  frame-locked следующий app update возвращает штатное false, пока существующая
  Board с vtable `820B728C` ещё ни разу не нарисована. Поле не подделывается:
  ожидается реальная первая отрисовка. Виртуальный LawnApp Update вызывается
  этим caller по `82478220..30`; существующий хук LawnApp не заменён.

Снимок T05 остаётся в прежней фазе after-root-update: вызов fixed fractional
выполняется после него. Равенство выбранной проекции двух диагностических
процессов не доказывает равенство изменённого режима обычной игре. Рендер,
input polling меню, загрузочные потоки и локальные RNG не становятся полностью
детерминированными автоматически. Остаточные расхождения, покрытие режимов и
проверка +1 sun описаны в [отчёте T05b](reports/T05b.md).

### Детерминированные часы Zen Garden (T05c)

`--pvz_deterministic_clock=1792195200` задаёт исходное время Unix в целых
секундах. Пустая строка отключает подмену; `0` допустим. Принимаются только
десятичные цифры без знака и пробелов, диапазон `0..2147471999`: это верхняя
граница штатного Xbox `time32` (`825F9600`, сравнение с `0x7FFFD27F`).
Неверное значение выдаёт ERROR и оставляет оригинальные часы; такую запись
нельзя принимать за успешный детерминированный запуск.

Xbox-путь Zen: `8228E618` (алгоритм GetPlantsNeed) вызывает `825F9600` по
`8228E694/8228E6D4`; тот вызывает `82616558` по `825F9618`, а thunk передаёт
управление `KeQuerySystemTime`, импорт `8275A65C`. Хук стоит на CRT-thunk
`82616558`, записывает 64-битный big endian FILETIME по исходному `r3`:

```text
116444736000000000 + unix_seconds * 10000000 + replay_step * 100000
```

Единица FILETIME — 100 нс, поэтому один логический шаг прибавляет ровно 10 мс.
До первого app logic счётчик равен нулю; он увеличивается перед корневым
update `8247FFC0`, когда app+5A7==0. Событие replay с номером N доставляется
после этого увеличения; во время его обработки часы видят N+1 шагов. Начало
`state.frame` остаётся другим, как описано выше. При паузе без app logic часы
не продвигаются. Сам флаг часов также включает учёт шагов, даже без replay.

Подмена действует на все обращения через этот CRT-thunk, включая запись
времени полива и проверки потребностей. Прямые импорты kernel time, host
таймеры планировщика, GPU и audio не меняются. Оригинальный `825F9600` по-прежнему
выполняет преобразование эпохи, целочисленное деление до секунд, проверку
диапазона и запись по необязательному output pointer. Флаг часов не включает
seed или frame replay автоматически. Для сравнения Zen нужны все три:

```text
--pvz_deterministic_seed=42
--pvz_replay_frame_locked=true
--pvz_deterministic_clock=1792195200
```

Нужно клонировать один исходный профиль для обоих процессов: timestamps в
сохранении — такие же входы, как seed и CSV. Одинаковый epoch сам по себе не
делает разные профили одинаковыми. При очень долгой симуляции после выхода
за диапазон Xbox `time32` оригинальный wrapper вернёт `-1`; такого прогона
не проверяли. Подтверждённое окно T05c — 5000 снимков Zen, две независимые
копии прежнего профиля T05b, побайтное равенство, включая metadata.
Адреса, команды, исходные SHA и ограничения — в [отчёте T05c](reports/T05c.md).
