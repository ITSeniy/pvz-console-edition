# T11b. Классы невиртуальных методов и пригодный план пакетов

**Этап:** знание · **Зависит от:** T11 (принята частично, см. `reports/T11-review.md`) · **Объём:** средний · **Меняет поведение игры:** нет

## Цель

T11 надёжно разметила виртуальные методы и конструкторы, но это лишь 15 % байт игрового
кода. Невиртуальные методы (у `Board` их сотни) остались `unknown`. План пакетов поэтому
свёлся к четырём «нераспределённым» пакетам с 82 % кода. Нужно поднять охват, не снижая
точности, и перестроить план.

## Что сделать

1. **Распространение типа `this` по графу вызовов.** Итерировать до неподвижной точки:
   - Функция получает класс X, если во всех её статических вызовах `r3` — это `this`
     метода класса X. Вариант с `r3`, неизменным от входа: medium при не менее чем двух
     разных вызывающих методах X и отсутствии вызывающих с другим типом. Один вызывающий —
     low.
   - `r3`, загруженный из поля известной раскладки T04 (`Board+1A4` → SeedBank и т. п.),
     даёт тип поля. Указать поле и инструкцию.
   - Конфликт типов — не угадывать: функция остаётся `unknown` с пометкой `conflict`.
   - Учитывать сдвиг `this` при множественном наследовании (`this_adjustment` из T11).
2. **Сигнатура полей.** Если функция обращается к `r3+offset` по набору смещений, который
   встречается только у одного класса из T04 и уже размеченных методов, это признак medium.
   Одно смещение — не признак.
3. **Сверка с Android и PC — только как подтверждение.** Для функции с классом по Xbox
   поискать одноимённый метод того же класса по совпадению вызываемых именованных функций и
   констант. Это даёт имя метода (medium), но не класс. Класс по одним Android/PC не
   назначать.
4. **Перестроить план пакетов.** Связи по вызовам — только справка. Пакет — класс или
   подсистема игрового кода и Sexy, ориентир 20–150 функций. Порядок задают:
   - доля листовых или чистых функций (их первыми берёт механизм T10);
   - связь с известными проблемами порта (`hook-inventory.csv`, README);
   - наличие PC-аналога;
   - риск: рендер, звук, платформа — в конце.

   Функции без класса не собирать в общие пакеты. Они идут отдельным списком
   `unassigned` с областью и размером.
5. Обновить `scripts/classify_xbox_functions.py`, CSV и отчёт. `--check` должен сохраниться.

## Результат

- `scripts/classify_xbox_functions.py`;
- `docs/native-port/data/xbox-function-classes.csv`;
- `docs/native-port/data/replacement-batches.csv`;

Только анализ, `src/` и `CMakeLists.txt` не трогать. Можно работать в общей папке.

## Критерии приёмки

- [ ] Точность не падает: выборка по `review.md` из 20 новых medium — не больше 2 ошибок,
      из 20 новых low — указана доля ошибок. Seed выборки указан.
- [ ] Доля байт игрового кода с классом medium+ — не меньше 50 %. Если не достигнута, отчёт
      показывает остаток по типам («нет вызывающих», «конфликт», «только косвенные вызовы» и
      т. п.) — тогда приёмка частичная.
- [ ] Каждое новое отнесение указывает инструкции и вызывающих, которые его доказывают.
- [ ] В плане нет пакетов из функций без класса. Каждый пакет содержит обоснование порядка
      по правилам п. 4. Пакеты не пересекаются.
- [ ] `--check` воспроизводит выходы побайтно; прежние high/medium T11 не потеряны (иначе —
      объяснение по каждой).
