# T07b — реализация повтора по логическим шагам

## 1. Итог

В отдельном worktree от `bf63a67873304bfd0d4875d96a28cb2ebcff02c2` добавлен
`--pvz_gamepad_repeat_fix=true`, по умолчанию false. Принятая бригадиром политика:
одно продвижение repeat-counter на логический шаг 100 Гц; направления повторяются
через 26 шагов, далее через 25/24/23/22/21/20 и затем каждые 20 шагов.
Это утверждённая политика порта, а не заявка на измеренный интервал физической Xbox.
Ни коммитов, ни изменения статусов README или ожиданий checkers нет.

Положительные и контрольные игровые прогоны выполнены одним замороженным EXE.
Логическая политика прошла полную матрицу; существующая проверка pc_settings_back
прошла пять раз подряд. Для буквального допуска в миллисекундах есть замечание
в §4.3.1. Обычные регрессии завершены: 275/276, единственный отказ — известный
pc_settings_back при выключенном исправлении, разрешённый карточкой.

```powershell

```

Для контроля повторить с новой копией того же профиля и fix=false, остальные
параметры одинаковы. Pause/Co-op: cursor_mode=console, свои CSV, 58/120 секунд.
Acceleration: cursor_mode=pc, 38 секунд. Старые T07 CSV — 62/56 секунд.
`services_settings_pad.csv` с флагом — пять свежих профилей, по 48 секунд.

из одного frame_limit. После каждой серии исходный режим 165 Гц восстанавливается.
Серия без VSync использует исходный монитор 165 Гц и pvz_vsync=false.
Одновременно работает только один игровой процесс.

## 4. Результаты

### 4.1. Источник частоты и решение владельца — проверено

Xbox `82580D88` вызывается из app pump через `8247CCDC..CCE4`, без привязки
к фиксированной частоте present. Порог сам по себе не задаёт миллисекунды.
Предыдущая принятая исследовательская часть T07b установила это по Xbox и
наблюдению Xenia (примерно 173 опроса/с с VSync и 320 без него).
Бригадир после исследования прямо выбрал 100 Гц, 26/25…20 шагов;
повторять шаг «Эталон» или менять выбранную политику не требовалось.

Использован существующий корневой логический счётчик: глобальный app `82D0BC88`,
его WidgetManager `+36C`, manager `+38`. `824A6140` вызывает `824A60F0`, затем
по `824A615C..6170` увеличивает `+38` и зеркалит в `+34`, перед вызовом
виртуального логического update (+28 vtable). `824A60F0` возвращает тот же r3;
это не счётчик draw или вызовов Gamepad. Логический источник соответствует
принятым T05b/T05c и продолжает работать при игровых паузах в меню.

### 4.2. Устройство исправления — проверено по всему телу Xbox

При fix=false и trace=false немедленно вызывается `__imp__sub_82580D88`.
При fix=true исполняется буквальная специализация оригинального тела Xbox
из `generated/default/pvz_recomp.92.cpp`. Нативной реализации опроса XInput,
обработки новых нажатий, отпусканий, осей или отключения не добавлено.

Для каждого из четырёх guest user slots запоминаются pad, manager и предыдущий
логический step. Разность unsigned step задаёт число ещё не учтённых шагов.
Новый pad, переподключение, смена manager или обратный ход счётчика начинают
новую эпоху; отключённое время не начисляется свежему нажатию. Обычное
переполнение uint32 обрабатывается unsigned-разностью.

Оригинальный 20-кнопочный repeat-loop исполняется для каждого накопленного шага.
При нулевом delta обход остаётся, но held-кнопка переходит к исходному next-button
до increment. Таким образом, не делается обратного декремента счётчиков.
Пороги 25 для направлений и 100 для остальных кнопок, рост repeat-count до 6,
его запись в counter после повтора, listener flags и алиасы сохранены.
Белого списка виджетов/меню/режимов нет: правило общее для всех получателей.

`verify-body.py` удаляет ровно объявленные вставки loop/gate/trace и сравнивает
**всё** оставшееся тело с оригиналом. Результат: равенство, сохранены
**1 GetState и 26 listener call sites**. SHA-256 original/restored нормализованного
тела одинаков: `d1939f2e19c76382ce1a7f75c51910c46b4a91e93df460b7e36d2efef1af1536`.
Доказательство — `runtime-data/wave2/body-proof.json`; исходные файлы не редактируются.

Изолированная проверка фактического RepeatSteps прошла **23 проверки**:
четыре независимых пользователя, delta 0/1/3, disconnect/reconnect, смена manager,
rewind, wrap и некорректный user. Использованы настоящий SDK PPCContext и sparse
guest memory; это проверка аккумулятора, а не подмена проверки игровых повторов.

### 4.3. Как считаются события

Каждое исходное down/up фиксируется после оригинальной обработки. Событие
repeat записывается непосредственно перед оригинальным listener-call.
Для D-pad считается raw flags=1; синтетический directional alias flags=3
не прибавляется второй раз. В контрольной original-ветви повторы распознаются
по исходному counter/repeat-count. Количество доставок в таблицах — initial down
плюс raw repeats, а не числовая разница соседних UI id (идентификаторы не подряд).
Границы UI и непрерывное движение игрового курсора рассматриваются отдельно.

Завершены **18 основных процессов**, по off/on для меню, паузы и Co-op
при каждой из трёх частот. В них **96 учитываемых удержаний с исправлением**,
в том числе 24 коротких: все 24 доставили одно нажатие и отпускание.
Все 48 первых повторов имеют разницу **26 logical step**; все последующие
интервалы секундных удержаний — **25/24/23**, policy_errors=0.

В таблице четыре числа означают 50/150/300/1000 мс. Co-op приведён отдельно
для каждого игрового пользователя: у обоих одна и та же последовательность.

| Режим | Получатель | off D-pad | off стик | on D-pad и стик |
|---|---|---|---|---|
| без VSync | PC Settings | 1/2/4/15 | 1/2/4/14 | **1/1/2/5** |
| без VSync | пауза | 1/2/4/15 | 1/2/4/15 | **1/1/2/5** |
| без VSync | Co-op P1, P2 | 1/2/4/15 | 1/2/4/15 | **1/1/2/5** |
| VSync 60 Гц | PC Settings | 1/1/2/8 | 1/1/2/7 | **1/1/2/5** |
| VSync 60 Гц | пауза | 1/1/2/7 | 1/1/2/7 | **1/1/2/5** |
| VSync 60 Гц | Co-op P1, P2 | 1/2/2/7 | 1/1/2/7 | **1/1/2/5** |
| VSync 100 Гц | PC Settings | 1/2/4/11 | 1/2/3/12 | **1/1/2/5** |
| VSync 100 Гц | пауза | 1/2/3/10 | 1/2/3/10 | **1/1/2/5** |
| VSync 100 Гц | Co-op P1, P2 | 1/2/4/12 | 1/2/4/12 | **1/1/2/5** |

Фактические down/up-интервалы отличаются от времён CSV из-за 25-мс цикла
публикации replay и фазы опроса. Диапазоны для 24 удержаний каждого номинала:
50 → **48–66 мс**, 150 → **129–166 мс**, 300 → **280–317 мс**,
1000 → **983–1021 мс**. Эти числа не заменяют исходные времена CSV и не
используются для изменения порогов. Сырые интервалы доступны в repeat-analysis.

У Co-op подтверждены mode79/scene3, оба user0/user1 до учитываемых удержаний,
а также действительное движение: P1 x=80/160/240 при y=130, P2 y=130/230/330
при x=720. При LB/RB packet P1 меняется между 0 и 3, P2 — между 0 и 1.
Эти результаты одинаковы с флагом при всех трёх частотах. Не следует выводить
число навигационных событий из расстояния: часть движений упирается в край поля.
Мышь↔pad дополнительно проверяется повторным открытием PC Settings мышью перед
каждым удержанием и переходом через паузу; в Co-op с двумя уже назначенными
геймпадами движение мыши не объявляется присоединением третьего игрока.

Основные доказательства: `runtime-data/t07b-implementation/v1/matrix-0/`
(settings/pause), `v3/matrix-0/` (Co-op), `v3/matrix-60/`, `v3/matrix-100/`.
Сводка: `python -I runtime-data/wave2/matrix-summary.py` → `matrix-summary.json`.
Setup-нажатия в chooser и финальные ownership probes не включены в 96 удержаний.

### 4.3.1. Миллисекунды и предел утверждения о задержке

Логическая политика выполнена точно, но строгую гарантию wall-clock
260±10 мс для каждого первого повтора объявить нельзя:

| Режим | Первый repeat от записи down, мс | Отклонение wall-clock интервалов от 250/240/230 мс |
|---|---:|---:|
| без VSync | 248–252 | −2…+2 мс |
| VSync 60 Гц | 250–251 | −13…+10 мс |
| VSync 100 Гц | 242–252 | −2…+2 мс |

При 60 Гц два из 24 интервалов отклонились более чем на 10 мс; при 100 Гц
один из 16 первых повторов зарегистрирован через 242 мс. Ничего не отфильтровано
ради прохождения допуска. Конкретный выброс: `v3/matrix-100/pause-on`, button17,
down step2993/ms93882755, repeat step3019/ms93882997,
`logs/smoke-20261017-214609-643.log`. Публикация исходного held в replay была
за 6 мс до записи down. Запись down сделана после обработки нового события,
repeat — перед его обработчиком: это не идеальные одинаковые точки измерения.
Фаза logical update относительно опроса и catch-up также могут влиять на мс;
разделить эти вклады данной трассой нельзя. Это объяснения для исследования,
а не доказанное оправдание выброса. Порог не увеличен и допуск не расширен.

Поэтому критерий частоты выполнен **по выбранным бригадиром logical steps**,
а его буквальная wall-clock часть отмечена ниже как частичная. Дополнительный
таймер, искусственно задерживающий callback после уже выполненных 26 шагов,
не вводился без отдельного решения: это было бы новым правилом доставки.

### 4.3.2. Ускорение, исходные реплеи и пять Back

Три дополнительных процесса (без VSync, 60 и 100 Гц), каждый с D-pad Down и
стиком Up на 3 секунды: первый repeat **26 шагов**, последующие интервалы
**25/24/23/22/21/20/20/20/20/20/20/20**. Все шесть длинных удержаний дали
14 raw доставок, policy_errors=0; все реплеи завершены. Каталоги:
`v3/acceleration-{0,60,100}/acceleration-on`.

Исходные `t07_settings_navigation.csv` и `t07_pause_navigation.csv` при 60 Гц
прошли в четырёх процессах off/on: replay_complete=true, survived/GPU=true,
fatal=0, неизменные исходные CSV. Доказательства: `v3/original-60/`.

`services_settings_pad.csv`, флаг включён, реальные 100 Гц, пять отдельных
процессов со свежими копиями одного baseline:

| Прогон | Реплей завершён | Исход существующего pc_settings_back |
|---|---|---|
| on-1 | да | true |
| on-2 | да | true |
| on-3 | да | true |
| on-4 | да | true |
| on-5 | да | true |

Во всех пяти журналах есть button4 found true, затем button0 found true;
исход совпадает с текущим условием checker, которое не изменялось.
Доказательства: `v3/settings5-100/pc-settings-back-on-{1..5}/{launch,smoke,result}.json`.
Всего в принятой feature-серии **30 игровых процессов**, без пробных неуспешных
launcher/chooser-запусков. После каждой серии, включая последнюю, Windows API
подтвердил возврат исходных 3440×1440/165 Гц.

Пробные запуски не скрыты и не включены в приёмку. В раннем launcher ошибочно
передавались два значения строкового pvz_cursor_mode, из-за чего не достигалась
готовность Title. Контрольные варианты изолировали эту ошибку тестового запуска;
не следует приписывать её repeat-loop. Дубликаты аргументов в runner запрещены.
Первый Co-op replay оставался в chooser; следующая версия запустила уровень,
но wait_board не завершался: этот существующий barrier публикуется только
для MouseUserIndex, которого нет при двух назначенных геймпадах. Новый replay
проверяется по фактическому mode79/scene3 до начала учитываемых удержаний.

### 4.4. Другие счётчики рисования — проверено частично

`Board::Draw 82146A60` инициализирует Board+560C по `82146B74` и увеличивает
его по `82146B80..94`. Соседние +5824/+5820/+5828 используются для оценки
частоты рисования по guest tick. CutScene `8217C5C8` читает draw-count
по `8217C7D8..E0`; зависимость первого update от Draw уже учтена T05b.
Следовательно, кроме Gamepad существуют состояния, зависящие от draw/present.
Это не доказывает ускорение всего игрового мира при 100 FPS. Исправление T07b
не переносит эти счётчики на другую частоту; полный аудит всех draw-потребителей
остаётся за рамками этого пилота.

## 6. Не проверено и риски

- Интервал физической Xbox в миллисекундах не объявляется нормативом.
- При задержке app pump накопленные шаги могут доставиться пачкой; хук не создаёт
  собственный поток событий между опросами. Реальный jitter приводится вместе
  с точными номерами logical step; пороги под него не изменяются.
- Буквальная специализация закреплена за данным Xbox-телом и SDK/generated ABI;
  при регенерации или смене образа необходимо повторить полное сравнение тела.
- Трасса меняет host timing; она выключена по умолчанию, обычные регрессии идут
  без неё. Совпадение расчёта repeat не означает исправление всех жалоб на FPS.
- Физические контроллеры и их hotplug в живом игровом процессе не проверялись;
  устройства replay и проверки аккумулятора не заменяют эту ручную проверку.

## 7. Вопросы к владельцу

Новых разрешений для реализации не требуется. Включать флаг по умолчанию,
менять checker pc_settings_back и переносить результат в master должен владелец
после приёмки; текущая работа этого не делает.
При приёмке отдельно учесть отклонения wall-clock из §4.3.1: точная политика

отдельного решения о поведении при фазовом сдвиге и догоняющих logical updates.
