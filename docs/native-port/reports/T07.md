# T07 — дополнительные шаги навигации при удержании направления

## 1. Итог

Воспроизведены два шага при одном 150-мс удержании направления как в паузе
Heavy Weapon, так и после PC Settings → Back. При 50 мс наблюдался один шаг,
при 300 мс — три; эффект есть и у D-pad, и у левого стика. По времени это
согласуется с быстрым штатным repeat Xbox. Дополнительное чтение живого Gamepad
подтвердило порог 25 и ускоренное продвижение счётчика: 186 приращений на
102 логических шага в выбранных непрерывных интервалах. Найдена virtual точка
опроса в app pump; полная связь её частоты с host pacing и причина всех
исторических исходов 0/1 ещё не изолированы.
**Расследование частичное: применять исправление пока рано.** Код игры,
проверки `scripts/check_*`, прежние реплеи и README не изменены.

### Чтение фокуса без хука и записи в процесс

В `matrix-2` и `pause-heavy` использован Win32 `OpenProcess(PROCESS_VM_READ)` /
`ReadProcessMemory`; `WriteProcessMemory`, debugger patch и остановки потока
не использовались. На этом EXE журнал сообщает virtual base `0x100000000`.
Прочитаны BE-слова:

```text
app     = read32be(base + 0x82D0BC88)
manager = read32be(base + app + 0x36C)
assert read32be(base + manager) == 0x8206404C
logic   = read32be(base + manager + 0x38)
focus   = read32be(base + manager + 0xA8)
vtable  = read32be(base + focus)
id      = read32be(base + focus + 0x6C)
up/down = read32be(base + focus + 0xB0 / 0xB4)
handler = read32be(base + vtable + 0xC0)
```

Сэмплы содержат UTC и host elapsed milliseconds. Запрошено ожидание 5 мс между
сэмплами; фактическая медиана в `matrix-2` — **16 мс**, а не 5. Метод не
обещает увидеть каждое мгновенное изменение; последовательности ниже разделены
на 125–158 мс. Источник `manager` проверен также в `src/state_dump.cpp:205`.
Существующий временный читатель можно запустить во **второй** PowerShell во
время smoke:

```powershell
./runtime-data/t07/read-focus.ps1 -Output runtime-data/t07-review-pause/focus.csv -Seconds 47
```

Для другой машины читатель следует воссоздать по указанным адресам, взяв base
из её журнала; он не является отслеживаемым результатом T07. Авторитетное
воспроизведение без него — replay + существующий listener + кадры; точное
время смены focus требует чтения памяти или указанных ниже breakpoints.

чтобы не выдавать неудачные измерения за подтверждение.

### Путь события и уровень доказательства причины

**Проверено по локальному коду порта/SDK:**

1. Физический путь выбирает SDL или XInput в `CreatePvzInputSystem`;
   диагностический флаг вместо него выбирает **один** `ReplayPad`.
   `PublishReplayPad` сохраняет buttons/axes, не генерирует повторные Down.
2. `ObservedDriver::GetDeviceState` регистрирует активность и переключает
   владельца; `Assignment` назначает устройства пользователю.
   SDK `InputSystem::GetState` объединяет состояния, а не рассылает события.
3. Xbox `822CB588` вызывает импорт `82759CBC` (`XamInputGetState`).
   `research/rexglue-source/src/kernel/xam/xam_input.cpp:95` передаёт запрос в
   `InputSystem::GetState`. `82580D88` опрашивает этот wrapper и разбирает кнопки.
4. Обработчик приложения `821ADC40` передаёт направление в `82477C88`, тот —
   в `824A6890`. Порт перед оригиналом восстанавливает фокус/доставляет mouse
   queue; исходный `824A6890` берёт focus `manager+A8`, вызывает vtable+C0.
5. У наблюдаемых GameButton/LawnStoneButton C0=`824AE388`; для направления
   он уходит в `82472DE0`. Последний выбирает навигационный сосед через
   vtable+B8 и меняет focus вызовом **`824A5F48`**.

**Проверено по Xbox, не по Android-смещению:** `82580D88:82580DDC..E60`
содержит autorepeat: для удерживаемой кнопки увеличивает счётчик,
сравнивает его с порогом, вызывает listener с **r6=1** и обновляет счётчик.
Начальный D-pad Down отправляется как button17 с r6=0 (`8258130C..358`),
затем как обобщённый button1 с r6=2; `82472DE0` различает эти флаги и
не навигирует вторично по обобщённому направлению с флагом 2. Поэтому сама
пара «raw D-pad + mapped direction» не доказывает двойную навигацию.

**Подтверждено косвенно:** дополнительные шаги возникают при продолжении
удержания, после приблизительно 0,13 с, при обоих источниках направления и
без движения мыши. Это соответствует autorepeat. У исходного replay нет
стика одновременно с D-pad: все четыре axes явно нулевые. Повтор порта и
двойная доставка SDL не нужны для воспроизведения на ReplayPad.

### Дополнительное прямое измерение native counters

**Проверено по Xbox:** vtable `Sexy::Gamepad` — `8207DA7C`, slot 14 (+38)
указывает на `82580D88`. Объект игрока 0 в этом запуске — `40005970`, user +4,
listener +8. Цикл `82580DDC..E60` читает held `+28+i`, увеличивает счётчик
`+3C+4*i` ровно один раз, сравнивает его с порогом `+DC+4*i`; при превышении
порога увеличивает repeat-count `+8C+4*i` (максимум 6), сбрасывает счётчик
в repeat-count и вызывает listener. Иные ветви этой функции инициализируют
или сбрасывают счётчик, а не добавляют ещё один tick.

**Проверено запуском:** восьмой отдельный процесс `live-repeat`, 60 с,
D3D12 инициализирован, пережил окно, fatal=0. Reader `read-gamepad.ps1`
читает блок 0x1B0 от начала Gamepad одним ReadProcessMemory и отдельно
manager/focus (размер allocation в constructor — 0x19C; 0x1B0 не размер ABI).
Получено **3161/3161** записей с ожидаемой vtable. Во всех held-сэмплах
направлений i=1 (стик Down) и i=17 (D-pad Down) порог **25**; у A/B i=6/7
порог **100**. Гипотеза о переключении порога направления на 12 не подтвердилась.

| Host ms от старта reader | Manager logic | Focus ID | D-pad counter | Порог |
|---:|---:|---:|---:|---:|
| 20325 | 2753 | 0 | 1 | 25 |
| 20387 | 2759 | 0 | 12 | 25 |
| 20451 | 2765 | 0 | 23 | 25 |
| 20465 | 2767 | 1 | 1 | 25 |

Первый дополнительный переход — через **140 мс / 14 logic**, с одновременным
сбросом native counter. Для 300-мс удержания переходы 0→1→2 наблюдаются на
30325/30465/30605 мс; для стика 0→1 — на 40323/40465 мс. Это прямое наблюдение
состояния native repeat, но регистры callback r3–r6 не перехватывались.

Для оценки скорости выбраны соседние пары, в которых B удерживается в обоих
сэмплах, счётчик не уменьшается и manager logic растёт. Порог 100 позволяет
исключить интервалы сброса. В **66** таких парах: **186** приращений counter,
**102** logic, **1031** host ms. Отношение **1,823529** counter/logic показывает
несколько продвижений счётчика между логическими обновлениями. Это выборочная
оценка, **не доказательство точных 200 Гц или ровно двух poll на каждый tick**.
Неатомарное чтение manager допускает пограничный сдвиг номера шага.

```powershell
# В отдельной консоли одновременно с новым settings smoke:
./runtime-data/t07/read-gamepad.ps1 -Output runtime-data/t07-review-settings/counters.csv -Seconds 58
python -I runtime-data/t07/analyze-counters.py
```

Для переноса reader на другую сборку найти объекты по vtable `8207DA7C`,
проверить user и listener; адрес `40005970` не является ABI-константой.
SHA counters.csv: `717ae22d271e8d7b0ada6a2cac4805ff791738f738b0e53dc677d816a9971858`;
reader: `ea34418ecbb1488c3a7f4165246332f71d2c295a3d62ebcc298e6a7190fd2cb1`.
Полный алгоритм статистики: по CSV суммировать положительные delta count7,
delta logic и delta ms для соседних held7=1 записей с delta logic>0.

**Причина раннего repeat подтверждена:** таймер native Gamepad продвигается
чаще логического WidgetManager, поэтому порог 25 достигается примерно за
14 логических шагов. `82583148`, вызываемый после app update, — `blr` stub,
а не доказанный вызов Gamepad. Историческая нестабильность одного CSV остаётся
отдельным неполностью изолированным эффектом настенных часов.

**Проверено по Xbox, дополнение к цепочке:** app constructor `82485030`
создаёт четыре Gamepad по `82485340..378` и кладёт указатели в app+34/38/3C/40.
Таким образом reader можно воспроизвести без hardcoded heap address:
`pad0=read32be(app+0x34)`, затем проверить vtable/user. `8247CB58` — app pump,
записанный в LawnApp vtable+184 (`820C02C0`). При app+550==0 цикл
`8247CCD4..CCFC` обходит четыре указателя и вызывает slot+38 каждого Gamepad
(вход Update `82580D88`, return LR `8247CCF8`). Это найденный virtual caller,
пропущенный анализом одних прямых bl. Pump вызывается через app slot+184 в
`82475DA8..DB0` и `824A87D4..DC`; дальнейшая стадия pump использует app slot+20
(`824799E0`), который отдельно планирует logic по времени. Полная статистика
вызовов pump и ветвей scheduler на живом процессе ещё не снята; равенство
одного poll одному manager tick из этого пути не следует.

```powershell
python -I scripts/name_xbox_from_android.py --inspect 82485030
python -I scripts/name_xbox_from_android.py --inspect 8247cb58
python -I scripts/name_xbox_from_android.py --inspect 824799e0
```

### Кандидат исправления — только текст, не применён

Предложение после прямого измерения: сохранить частый опрос состояния и
доставку новых edges, но продвигать **таймер направления меню** один раз за
логический tick manager. Пропуск всей функции Gamepad::Update теряет короткие
нажатия; фильтр «не более двух переходов за кадр» не помогает, поскольку
переходы разделены 14 кадрами. Увеличение задержки до произвольных 300 мс
также не исправляет источник ускоренного счёта.

Ниже проект вставки в `src/mouse_bridge.cpp`, использующий его существующий
TopRootWidget. Он компенсирует именно дополнительный `+1` цикла native repeat
на повторном poll в том же manager tick; XInput и callback edges исполняются
оригиналом. Порог 25 и repeat-count сохраняются. Это **не применённый и не
испытанный патч**, а конкретный кандидат для следующей приёмки.

```diff
+REX_EXTERN(__imp__sub_82580D88);
+namespace {
+struct MenuRepeatTick {
+  uint32_t pad = 0, manager = 0, root = 0, tick = 0;
+  bool valid = false;
+};
+std::array<MenuRepeatTick, 4> menu_repeat_ticks{};
+}
+REX_HOOK_RAW(sub_82580D88) {
+  const uint32_t pad = ctx.r3.u32;
+  const uint32_t user = Read(base, pad + 4);
+  if (user < menu_repeat_ticks.size()) {
+    auto& seen = menu_repeat_ticks[user];
+    const uint32_t app = Read(base, 0x82D0BC88);
+    const uint32_t manager = app ? Read(base, app + 0x36C) : 0;
+    const uint32_t root = manager ? TopRootWidget(manager, base) : 0;
+    const uint32_t vt = root ? Read(base, root) : 0;
+    if (vt == 0x820BAA54 || vt == 0x820C4ABC) {
+      const uint32_t tick = Read(base, manager + 0x38);
+      if (seen.valid && seen.pad == pad && seen.manager == manager &&
+          seen.root == root && seen.tick == tick) {
+        for (uint32_t i : {0u, 1u, 2u, 3u, 16u, 17u, 18u, 19u})
+          if (base[pad + 0x28 + i]) {
+            const auto at = pad + 0x3C + 4 * i;
+            // u32 wrap is intentional: native addi restores zero too.
+            pvz::guest::Write(base, at, Read(base, at) - 1u);
+          }
+      }
+      seen = {pad, manager, root, tick, true};
+    } else seen.valid = false;
+  }
+  __imp__sub_82580D88(ctx, base);
+}
```

Перед применением проверить единственный поток/нерекурсивность этого virtual
update, все записи timer-полей, переполнение tick и повторное использование
адреса Gamepad. Ограничение двумя подтверждёнными корнями намеренное: Board
и остальные меню требуют отдельных проверок. Выход из меню сбрасывает cache;
release/новый edge остаются в оригинале. Проверить Down/Up, 50/150/300 мс,
долгое удержание, оба игрока, смену мыши/геймпада, появление нового меню между
двумя poll, FPS/throttling. Кандидат задаёт политику одного timer tick на logic;
ожидаемая политика оригинального Xbox ещё требует сравнения с консолью.
Без этих проверок критерий «патч устраняет причину» **не выполнен**.
Ожидания services и пороги проверок не менять ни на ID0, ни на ID1.

### Польза имён T01

Принятый экспорт T01 не содержит консольные классы ввода (это прямо отмечено
в его приёмке). Поэтому нельзя утверждать, что он уже именовал этот путь.
Имена WidgetManager, GameButton/ButtonWidget, Widget, HelpOptionsDialog,
NewOptionsDialog из существующего RTTI/inventory и комментариев помогли выбрать
slot C0, навигационные ссылки и точку focus. Их роль дополнительно проверена
по приведённым Xbox-вызовам и живым vtable/handler.

`GamepadControls::OnButtonDown` не оказался обработчиком кнопок открытой паузы:
там фокус у LawnStoneButton, C0=`824AE388`. Это не доказательство неверного
имени gameplay-функции, а другой маршрут события. Именам `GamepadApp` и
`Gamepad::UpdateStates` здесь соответствует исследовательская роль, точная
Xbox C++-сигнатура/класс `82580D88` не объявляются результатом принятого T01.
Новых неверных **экспортированных** имён T01 в рамках T07 не установлено.

## 5. Критерии приёмки

- Воспроизводимый сценарий: **выполнен** — два новых replay, матрица settings
  повторена дважды, пауза воспроизведена; неуспешная Adventure-подготовка раскрыта.
- Причина подтверждена наблюдением с адресами: **частично** — дополнительные
  focus transitions и интервалы подтверждены живым чтением и listener;
  native counter/порог прочитаны напрямую, ускорение относительно logic подтверждено.
  Virtual caller найден по Xbox, но его полная частота и историческое плавание
  одного неизменного replay не изолированы.
- Патч устраняет причину: **не выполнен** — предложена нормализация timer tick,
  но её соответствие Xbox-политике и отсутствие потери edges не проверены;
  код не применён и кандидат не проверен. Маскировать проблему кадром нельзя.
- Польза и ошибки имён T01: **выполнен** — отделён принятый узкий экспорт от
  RTTI/комментариев и гипотез, указан фактический маршрут паузы.

## 6. Не проверено и риски

- Физические SDL/XInput устройства, одновременные реальные мышь/геймпад и
  подавление дрейфа не проверялись. ReplayPad устраняет физический бэкенд
  из данного воспроизведения, но не доказывает отсутствие отдельных его ошибок.
- Отдельные режимы 60/100 FPS, 100-Гц монитор и throttling не сравнивались.
  Измерены manager update и выборочное продвижение native timer;
  точная частота каждого virtual вызова и Present/FPS не измерена.
- Reader не делает атомарный snapshot всех слов; 16-мс дискретность и порядок
  отдельных чтений допускают пограничный сдвиг номера logic на 1–2 шага.
- Новые replay идут по wall clock с опросом 25 мс. Поэтому пограничные 120–150 мс
  не являются детерминированным тестом. Решение T05b может дать следующий опыт,
  но его новый EXE в эти результаты не входит.
- Прежняя игра/проверки не менялись; обычные CTest/полные регрессии не повторялись,
  поскольку здесь нет сборки или изменения runtime. Читатель фокуса не писал
  память процесса. Исправление не оттестировано и не объявляется готовым.

## Приёмка (17.10.2026)

**Итог: расследование принято; кандидат патча не принят — нужна задача T07b.**

- Причина подтверждена хорошо: автоповтор `82580D88` (`Sexy::Gamepad` vtable `8207DA7C`,
  slot 14) прибавляет счётчик на каждом опросе. Опросов около 1,8 на логический шаг
  (186 на 102), поэтому порог 25 достигается примерно через 0,13 с. Матрица
  50/150/300 мс → 0/1/2 лишних шага повторена дважды, есть адреса и время. Это объясняет
  и плавание 0/1 в `pc_settings_back`: удержание около 150 мс стоит на границе порога.
- Замечания к патчу:
  1. Он нормирует повтор к логическому шагу (100 Гц), но эталон — частота опроса на
     консоли. Если Xbox опрашивал раз в кадр при 60 Гц, задержка повтора там около 0,42 с;
     нормировка к 100 Гц даст около 0,25 с — всё ещё быстрее консоли. Сначала установить,
     кто и с какой частотой вызывает `82580D88` на Xbox (вызывающая точка в app pump
     найдена; частоты present есть в измерениях T08).
  2. Декремент счётчика задним числом и белый список двух корневых виджетов хрупки, а
     автоповтор действует и на поле (консольный курсор, перебор карточек). Лучше
     накапливать время и продвигать повтор с консольной частотой для всех получателей.
  3. Возможна связь с жалобой тестеров на ускорение при 100 FPS — проверить в T07b.
