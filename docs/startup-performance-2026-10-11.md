# Требования и задержки загрузки — 11.10.2026

Продолжение сессии Claude `e67f3cf2-a661-4d04-832a-ab77395acdff`.

Для Windows x64 нижняя граница инструкций проекта — SSE4.1: её использует
`roundevenf` и настройки ReXGlue. SSE4.1 теперь явно включена и для clang-cl;
`/Ob2` разрешает полное встраивание небольших функций рекомпилированного кода.
Глобальные AVX/AVX2-флаги не добавлены. Наличие AVX-инструкций в готовом файле
само по себе не доказывает требование AVX: CRT содержит выбираемые по CPU
варианты функций. Проверки на процессоре без AVX ещё не было.
Настройки SDK: [ReXGlue 0.10.0](https://github.com/rexglue/rexglue-sdk/blob/v0.10.0/cmake/rexglue_helpers.cmake).

GPU должен предоставлять Direct3D 12 с Feature Level 11_0 или выше: именно
этот уровень запрашивает [D3D12Provider SDK](https://github.com/rexglue/rexglue-sdk/blob/v0.10.0/src/ui/d3d12/d3d12_provider.cpp).
Feature Level 12_0/12_1, RTX и ROV не являются общим обязательным порогом.
Это проверка совместимости API, а не обещание 60 FPS на любой такой карте.
Минимальные модели CPU/GPU и объём памяти по результатам нескольких машин
ещё не установлены. Тестовая машина: Ryzen 7 5700X, RTX 3070.

Убирать SSE4.1 только из `roundevenf` недостаточно: нужно пересобирать и
проверять SDK. Замена GPU-бэкенда также требует отдельной проверки рендера.
Поэтому совместимость уточнена до фактической границы API, а ускорение
сделано в существующем пути вывода кадров.

## Что задерживает старт

Профилирование зафиксировало три разных источника: ожидания игрового потока
во время загрузки ресурсов, создание GPU-ресурсов/ожидание очереди и обработку
ресурсов меню. В прежнем пути каждый повторный DXGI Present ждал VBlank;
это задерживало общую GPU-очередь даже во время загрузки, когда нового
игрового кадра ещё не было. Теперь SyncInterval=1 применяется к новому
игровому кадру, повторный вывод использует 0 с запретом tearing при VSync.
Неуспешный неблокирующий Present не помечает кадр синхронизированным.
Семантика параметров: [Microsoft Present](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/nf-dxgi-idxgiswapchain-present).

В сохранённых прогонах Claude длинный интервал при прогретом кэше составлял
2170 мс, после правки — 227–305 мс. Холодный запуск до правки давал 3589 мс.
При загрузке также остаётся отдельный интервал порядка 420–460 мс; правка
вывода не устраняет ожидания ресурсов. После перехода в меню выдача кадров
держится на 60 FPS, обычный максимальный интервал — около 17–20 мс.
Это замеры на одной машине; они не измеряют физическую плавность монитора.

Журналы: `runtime-data/refactor-check/startup-warm-200346/run.log`,
`startup-cold-200306/run.log`, `vs-fix1-201610/run.log`, `vs-fix2-201638/run.log`,
`resume-startup-pvz-ob1-002841/run.log`,
`resume-startup-pvz-console-edition-002909/run.log`.
Сравнение `/Ob1` и `/Ob2` в последней паре не показало убедительного
уменьшения задержек загрузки; основное измеренное улучшение относится к VSync.

`--pvz_hitch_profile=true` включает диагностический сбор стеков при
отсутствии игрового кадра более 50 мс. По умолчанию сбор выключен;
буфер ограничен, поток профилирования завершается при закрытии приложения.
Диагностика сама влияет на тайминг и не предназначена для обычной игры.

цели вне окна и прекращает вращение колёс после достижения малой скорости.

и `feedback_izombie_sun_fast.csv`; свежие результаты — в
`runtime-data/session-completion-runs.json`.

20/20 целевых проверок в `runtime-data/session-completion-checks.json`.

обе границы движения Heavy Weapon и его остановка, лопата, цикл VSync,
выбор/отмена/повторный выбор карточки Slot Machine. В I, Zombie приняты
все 360 быстрых нажатий и 360 отпусканий, собраны восемь солнц.

ZIP проверен по манифесту: 97 файлов, EXE совпадает с текущей сборкой.

В I, Zombie проверяется выпадение солнц из поедаемых подсолнухов.
Границы попадания совпадают с PC-моделью: размеры объекта плюс 15 пикселей
для обычного солнца; уже собирающееся солнце не перехватывает следующий клик.
