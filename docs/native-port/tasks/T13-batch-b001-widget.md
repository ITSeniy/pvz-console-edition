# T13. Первый пакет замен: B001 `Sexy::Widget`

**Этап:** пакеты замен · **Зависит от:** T10, T11b, T12 (приняты) · **Объём:** средний · **Меняет поведение игры:** только под флагами

## Цель

Первый пакет по плану `data/replacement-batches.csv`. Главная цель — **отладить процесс
работы пакетами** и измерить его стоимость, а не набрать объём нативного кода. По итогам
решаем размер и порядок следующих пакетов.

## Состав

Пакет B001: 68 функций класса `Sexy::Widget` (список — колонка `members`). Из них:

- 66 отнесены к классу по RTTI (high), 2 — по записи vtable (medium);
- 29 функций не длиннее 8 байт (заглушки: `blr`, возврат константы);
- у всех есть одноимённый метод в PC-декомпиляции (`research/pvz-pc/SexyAppFramework/Widget.cpp`);
- `82473000` уже перехвачена портом (`hook-inventory.csv`).

## Что сделать

1. **Разбор каждой функции.** Для каждой из 68 по Xbox-коду:
   - имя метода, если оно доказуемо (слот vtable по T01/T01b, принятые имена); иначе
     `Widget_<адрес>`;
   - ABI: входы, выходы в регистрах и памяти;
   - дочерние вызовы и побочные эффекты;
   - режим проверки — `DeclaredOutputsOnly` (сравнение) или `SnapshotsOnly` (только снимки
     состояния).

   Функцию, которая вызывает виртуальные методы, `WidgetManager`, звук или пишет за пределы
   объявленных диапазонов, сравнивать нельзя: только `SnapshotsOnly`.
2. **Уже перехваченные функции** (`82473000` и все, что найдутся по `hook-inventory.csv`) не
   заменять повторно. Описать, что делает существующий хук, и оставить как есть.
3. **Реализация.** Один файл `src/native/b001_widget.cpp` на механизме T10. Логика — по
   Xbox-коду. PC-исходник (MIT) можно использовать как ориентир, поля — только из `src/xbox/*.h`.
   Если поля нет в раскладках T04, добавить его в `src/xbox/Widget.h` с доказательством
   (`адрес инструкции — функция — смысл`) и строкой в `data/xbox-layouts.csv`.
4. **Флаг пакета.** Добавить в механизм T10 общий флаг пакета: `--pvz_native_b001=true`
   включает все замены пакета, `--pvz_native_b001_compare=true` — сравнение. Имя пакета
   передаётся при объявлении замены. Флаги отдельных замен сохраняются.
5. **Проверка одним прогоном.** В `run_native_proof.ps1`:
   - режим `-Batch b001` — все замены пакета;
   - отрицательный контроль одним прогоном: `inject_error` для всех замен сразу, при этом
     каждая замена с ненулевым охватом должна дать свою ошибку;
   - сводка по каждой функции: охват, ошибки, режим.

   Пятикратный прогон отрицательного контроля на каждую функцию не нужен.
6. **Охват.** Функция без реальных вызовов в пяти сценариях не считается заменённой: она
   остаётся в файле, но помечается `unproven` и в флаг пакета не входит. Если охват можно
   получить готовым реплеем (`tests/replays/menu_hover.csv`, `input_ownership.csv`,
   сценарии Services), добавить его в proof — без записи новых реплеев.
7. **Таблица статусов.** `docs/native-port/data/native-replacements.csv` — одна строка на
   функцию: адрес, пакет, имя, режим, статус (`replaced`, `unproven`, `existing-hook`,
   `skipped`), охват, ошибки, причина. Таблица будет общей для всех следующих пакетов.

## Измерить для планирования

- Время разбора и реализации на функцию: заглушки отдельно от остальных.
- Время одного прогона proof для пакета.
- Доли `DeclaredOutputsOnly`, `SnapshotsOnly`, `unproven`, `existing-hook`.
- Что мешало: поля без раскладок, виртуальные вызовы, отсутствие охвата.

## Важно про рабочие деревья

Рабочие деревья этого репозитория содержат junction-ссылки на основную папку (`assets`,
`generated`, `.cache`, `tools`, `research` и папки с образами игр). **Не удалять** worktree и
эти папки рекурсивно: удаление проходит по ссылке и стирает данные основной папки. Если
worktree нужно убрать, сначала снять каждую ссылку (`cmd /c rmdir <ссылка>`), убедиться, что
ссылок не осталось, и только потом удалять.
