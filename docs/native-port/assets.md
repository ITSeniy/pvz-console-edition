# Ресурсы нативного порта: форматы и границы чтения (T09)

Проверено 2026-10-17 на текущей копии Xbox XBLA `584109FF` и Android TV 1.1.5.
Восстанавливаемое доказательство — `research/cross-platform/native-assets/inventory.json`;
команды и SHA-256 приведены в [отчёте T09](reports/T09.md). Уровни ниже:
**проверено** — чтение предоставленных байтов или дизассемблирование Xbox;
**косвенно** — вывод по сопоставлению; **неизвестно/гипотеза** — ещё требует исследования.
Проверка формата в Python не означает наличие загрузчика этого формата в нативном порту.

## Эффекты Xbox и Android

**Проверено:** каждому из 195 `sounds/*.xma` соответствует ровно один Android
`sounds/*.wav`; пропусков и лишних WAV нет. SHA-256 реальных WAV совпали с Android-инвентарём.
Имена устанавливают пары; вывод о содержании опирается на измерения ниже.

| Метрика | Xbox | Android |
|---|---|---|
| Формат | XMA2 | PCM, 8 бит |
| Частота | 189 × 44100, 2 × 48000, 2 × 22050, 1 × 11025, 1 × 8000 Hz | 195 × 22050 Hz |
| Каналы | 42 mono, 153 stereo | 195 mono |

Частота совпадает у **2/195**, число каналов — у **42/195**. Длительность XMA
рассчитана по `PlayLength / SamplesPerSec`, а не по padded `SamplesEncoded`;
для PCM — по числу фреймов данных. Медиана абсолютного расхождения —
**0,000453515 с**, максимум **0,199863946 с** у `tapglass`: Xbox **0,545668934 с**,
Android **0,345804989 с**. Следовательно, равенство длительности всех пар неверно.

Имеющийся FFmpeg 8.1 декодировал **20/20** пар без ошибок возврата и нечисловых
сэмплов. Метод воспроизводим: `random.Random(20261017).sample(sorted(names), 20)`;
оба потока → mono 22050 Hz float32; максимум нормированной Pearson-корреляции
в пределах ±2205 сэмплов (100 мс), перекрытие не меньше 90% короткого сигнала.
Временного растяжения нет. Все найденные сдвиги равны нулю.

либо предварительная конвертация, без обязательного наличия Android-образа.

## Музыка

**Проверено по заголовкам и путям:** в Xbox пять музыкальных файлов, все в `sounds/`.

| Xbox-файл | Байт | Формат/структура | Тот же логический путь в Android |
|---|---:|---|---|
| `mainmusic.xm` | 20778068 | XM 1.04: 236 orders, 200 patterns, 82 instruments | Нет |
| `mainmusic_drums.xm` | 4101796 | XM 1.04: 16 orders, 16 patterns, 11 instruments | Нет |
| `mainmusic_hihats.xm` | 600798 | XM 1.04: 236 orders, 200 patterns, 56 instruments | Нет |
| `zombiesonyourlawn.ogg` | 1612125 | Ogg/Vorbis, английские титры | Да, 950575 байт; encoded SHA-256 различается |
| `zombiesonyourlawn_jp.ogg` | 3065020 | Ogg/Vorbis, японские титры | Нет |

Android содержит **три**, а не два музыкальных Ogg:
`music/crazydave.ogg` (523885 байт), `music/day.ogg` (1254357 байт),
`sounds/zombiesonyourlawn.ogg` (950575 байт). Последний легко пропустить при
поиске только в каталоге `music/`. Это уточняет прежний вывод
`docs/native-port-feasibility.md`; тот исторический файл в рамках T09 не менялся.

Четыре Xbox-пути отсутствуют в Android. Это **не** доказательство отсутствия
каждой мелодии из XM: tracker-модули содержат несколько секций, а drums/hihats —
отдельные слои. Сопоставление игровых Tune ID с orders ещё не выполнено;
список названий эксклюзивных мелодий неизвестен. Различный SHA английских Ogg
доказывает различие кодированных файлов, но не различие исполнения песни.
Для собственного плеера нужны XM-воспроизведение, управление секциями/слоями и Vorbis.

## PAK, XCTD и собственная распаковка

| Пакет | Записей | Внешний слой | XCTD segments | Размер внутреннего PAK |
|---|---:|---|---:|---:|
| de.pak | 175 | XCTD | 31 | 17336720 |
| en.pak | 21 | Обычный PAK | — | 1945488 |
| es.pak | 169 | XCTD | 25 | 16365968 |
| fr.pak | 171 | XCTD | 27 | 17385872 |
| it.pak | 156 | XCTD | 25 | 15980944 |
| jp.pak | 204 | XCTD | 45 | 23702288 |
| main.pak | 3208 | XCTD | 408 | 219849604 |
| na.pak | 0 | Обычный PAK | — | 9 |

**Проверено:** внутренние PAK читаются `analyze_cross_platform.py:pak_entries`
до точного EOF. Заголовок `C0 4A C0 BA 00 00 00 00`, далее флаг записи,
uint8 длины имени, ASCII-имя, LE u32 размера, 8 байт FILETIME; `0x80` завершает
каталог. Перед каждым payload — LE u16 длины padding и сам padding.
Режим Sony дополнительно читает expanded size/zlib и не является Xbox-режимом.

Для шести XCTD кэши QuickBMS проверены по **обоим** SHA-256 из `.pak.meta.json`:
исходный файл и распакованные байты. `decode_xctd` использует QuickBMS
`comtype xmemdecompress`; метаданные прямо отмечают `crc_verified=false`.
Для `main.pak`:

- исходный SHA-256: `ab5586a8fb2b54bfb78f2d05754d2d0112595182b9cc080ecf9a113eca91966e`;
- распакованный: `c43eb9e1aa5686c25e5b44ff11841b1619f3934bc3a0ccc8a87417c85cf29f04`.

Разбор заголовка, таблицы и размеров **проверен на 6/6**. Правила chunk stream
ниже взяты из существующего исследовательского `research/cross-platform-tools/xctd_rip.cpp`
и подтверждены его успешными распаковками только **4/6**:

- Заголовок 16 байт BE: magic `0x0FF512ED`, u16 version `0x0100`, u16 reserved,
  u32 CRC/hash неизвестного вида, u32 flags.
- `window = 1 << ((flags & 15) + 15)`, zone/pad `0x8000 << ((flags >> 4) & 3)`;
  у всех шести оба значения `0x20000`.
- Число сегментов `(flags >> 6) & 0xffff`. Разрядность таблицы длин — 32 при
  ненулевых bits 22–23, иначе 20; здесь только **32**, 20-битный вариант не проверен.
  Таблица BE, сумма длин совпадает с распакованным размером.
- Далее framed LZX: BE16 длина compressed chunk, до 32 KiB результата на frame,
  сброс окна между сегментами, различение contiguous/zoned размещения и padding.

Существующий локальный `xctd_rip.exe` проверен на всех шести пакетах. Для
**de/es/fr/it** выход побайтно совпал с эталоном по SHA-256. Для **jp** — exit 6,
`segment 5 frame 0 bad chunk size 0 at 0xa0000`; для **main** — exit 6,
`segment 178 frame 0 bad chunk size 0 at 0x1640000`. Нельзя объявлять этот
инструмент готовым распаковщиком Xbox-копии: framing/padding ещё не закрыт.

| Пакет | Поле CRC/hash | CRC32 распакованных байтов |
|---|---|---|
| de | `d5059579` | `148fafa0` |
| es | `04bea074` | `68eb7e03` |
| fr | `706c781f` | `7136a11f` |
| it | `c156ca92` | `0e73f5f1` |
| jp | `52e36f4a` | `5b9237cb` |
| main | `81c94d5d` | `9120404f` |

**Проверено:** обычный CRC32 всего декодированного потока не совпал ни разу.
Алгоритм поля и покрываемые байты **неизвестны**, контроль целостности XCTD
не реализован. SHA кэша подтверждает воспроизводимость конкретного результата,
но не заменяет исходную проверку CRC.

Для собственного распаковщика остаются: полное framing/padding на main/jp;
LZX/XMem с нужными окнами и reset; проверка границ и повреждённых потоков;
разбор CRC/hash; затем шесть эталонных совпадений и внутренний PAK-reader.
`research/rexglue-source/src/system/lzx.cpp` — справочник по LZX/XEX, не готовый
XCTD-reader. Локальный research-ripper использует patched libmspack (LGPL-2.1);
его код не переносился в порт. `xctd-upstream.py` изменяет входы на месте,
в T09 не запускался и для read-only инвентаризации не подходит.

## Сохранения и переносимость

### Профиль Xbox

**Проверено по файлам и существующим скриптам:** runtime содержит три бинарных
payload в `runtime-data/user/584109FF/profile/User/`:

| Setting ID | Байт payload | Известное |
|---|---:|---|
| `63E83FFD` | 160 | Бинарная настройка; полная схема неизвестна |
| `63E83FFE` | 1000 | Бинарная настройка; полная схема неизвестна |
| `63E83FFF` | 850 | BE u32 version 19 по +0, Adventure level по +4, coins/10 по +8 |

Отдельные Xenia-файлы в `save/` имеют дополнительно 24 байта: BE setting ID
по +0, type 6 по +8, BE payload size по +16, затем payload с +24.
Их размеры 184/1024/874 байта. Два ZIP прочитаны, хеши всех членов записаны.
`584109FF.zar` (1291 байт) имеет Zstandard magic `28 B5 2F FD`; его контейнер
в T09 не распаковывался, содержимое заново не подтверждено.

`scripts/import_xenia_profile.py` проверяет ID, тип, размеры и version и снимает
обёртки из папки/ZIP. `scripts/export_test_profile_to_xenia.py` разбирает XDBF/GPD
и создаёт binary settings для Xenia. `scripts/make_level_save.py:make` меняет
уровень профиля; это не генератор полного Board SaveGame. Ни один из этих
инструментов не является конвертером PC/Android-сохранений.

### Игровой SaveGame

В текущем `.../pvz_savegame.dat/game_0.dat` (83030 байт) **проверено**:

| Смещение | Содержимое |
|---:|---|
| 0–19 | SHA-1 байтов с +20 до конца: совпадает |
| 20 | LE u32 `12`, длина следующего raw header |
| 24 | BE u32 magic `0xFEEDDEAD` |
| 28 | BE u32 version `8` |
| 32 | BE u32 `0xC8CEBCAA`, назначение как build-date/hash — гипотеза по PC |
| 36… | Состояние Board; полная схема не разобрана |

SHA-256 образца: `b241bc5f06f1b44efa271ab10865ccf7bf94ab034cb5ede13ce23a337d8160cc`.
Смешанный порядок байтов исключает простую замену endianness всего файла.
Проверка SHA-1 относится к этому образцу, общий алгоритм записи ещё не восстановлен.

**Xbox-код проверен:** `0x82205890` загружает 12 байт header через SyncBytes
`0x82204678`, проверяет magic и принимает только version **8**, затем вызывает
SyncBoard `0x82204E48`. Третье слово в этом месте не сравнивается.
SyncBytes использует SyncInt `0x82204718` для длины и byte-read/write
`0x824B62F0`/`0x824B6F18` для тела; SyncBoard включает raw-массивы и конечный
маркер `FEEDDEAD`. Полная сериализация объектов этим наблюдением не установлена.

**Справочники других веток:** PC
`research/pvz-pc/Lawn/System/SaveGame.cpp:19–21,509–511` проверяет magic,
version **2** и CRC32 build-date; raw-структуры зависят от `sizeof(T)`.
Android-символ `LawnLoadGame(Board*, SaveGameContext*)` `0x00143B65` (Thumb)
тоже читает 12 байт и сравнивает version **8** (`0x00143BA4`), затем вызывает
SyncBoard (`0x00143BD0`); SyncBytes `0x001426B1` передаёт тело Buffer::ReadBytes
`0x002F7CE5`, который копирует байты через `strb` без перестановки слов.
Это совпадение семейства формата, а не доказательство совместимости layout.

**Вывод:** прямой формат Xbox ↔ PC несовместим уже по version и raw header.
У Android совпадает version, но ARM/Xbox имеют разные раскладки объектов и
порядок байтов raw header; бинарную совместимость использовать нельзя.
Файла Android SaveGame среди проверяемых входов нет: реальная загрузка/конвертация
не проверялась. Для миграции нужен разбор полей, размеров, ссылок, профиля и
внешних проверок целостности, затем отдельный writer целевой платформы.

## Что ещё требуется нативному пути

Инвентаризация не добавляет runtime-загрузчиков. Открыты XCTD/CRC, Xbox Tod
`.compiled`, диалект XML и шрифтов, XMA2, XM с управлением музыкальными слоями,
профили и полный Board SaveGame. Для текстур проверен текущий базовый формат;
ресурсные ID, атласы, локализации, рендеринг и потоки воспроизведения требуют
собственной интеграции. Входные пакеты, образы, профили и сохранения не изменены.
